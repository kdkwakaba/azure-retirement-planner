# リリース計画・手動CD

## 対象と実行範囲

[AGENTS.md](../../../AGENTS.md)と[開発・運用基準](../../../docs/engineering.md)を確認する。依頼が計画・検証・実行のどれか、環境、Subscription／専用RG、Commit、成果物、Workflowを特定する。既に得た承認は再要求しないが、Skillの呼出自体を未知の実環境への包括許可と解釈しない。

実装済みWorkflow・IaCと[Runbook](../../../docs/runbook.md)を確認する。配置済み環境でも、Bootstrap、接続先、秘密、モデル提供条件を確認してから実行する。欠落を成功扱いしない。

## 事前確認

- 検査済みmainの正確なCommitと成果物Hashを使用し、未Commitの作業を混ぜない。
- 要件充足、必要テスト、型・ビルド、最新の依存脆弱性・サポート検査を確認。古いビルドの監査成功だけで現在も安全としない。
- IaCパラメーター、Prompt／Rule／Schema／Model版、設定差分、必要秘密の参照を記録。秘密値は出力しない。
- OIDCと用途別Identityを確認。Bootstrap権限と通常CDを分け、対象Azure読取Identityをデプロイに転用しない。
- What-ifは対象と権限を確認して実行し、作成・変更・削除、不明／評価不能をレビューする。無料・読取権限だけで実行可能とは仮定しない。
- 専用RG外や共有・評価対象の変更、予期しない削除、RBAC拡大、課金追加、データ破壊があれば止め、具体的差分を人間へ示す。
- 個人非公開GitHubで利用できない承認保護を前提にしない。manual dispatchは第三者の強制承認とは区別する。

## 適用

既存の明示的な承認が対象・Commit・差分をカバーしていれば進める。足りなければ具体的計画を提示し、該当操作だけ確認する。通常のテスト・読取のたびに確認しない。

実在する手動Workflowを使い、IaC反映、同じ検査済成果物の配置、疎通・認証・認可・根拠・再実行確認の順に進める。環境単位で同時デプロイを直列化する。承認や対象が変わった場合は改めて確認する。

配置後試験で有料推論やGitHub作業登録を行う場合、対象・データ・件数・予算が許可されていることを確認する。実データやTokenをActions Artifact／ログへ保存しない。

## 失敗・完了

権限、版、根拠・承認、検査に不適合があれば先へ進めない。外部作成の応答不明は照合し、盲目的に再作成しない。原因未特定のデプロイを繰り返さない。

アプリ前版の再配置とデータ／IaCの復旧を区別。互換性と実行承認がある場合のみ前版を使用する。不可逆なデータ変更やAzure削除を自動Rollbackとしない。

環境、Commit、成果物Hash、各Version、What-if確認、承認根拠、実行Run、疎通・検証結果、失敗・復旧状況、残課題を秘密なしで報告する。配置失敗や未検証を成功として扱わない。
