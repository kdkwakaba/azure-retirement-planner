# セキュリティ保守

## 調査対象

[AGENTS.md](../../../AGENTS.md)と[開発・運用基準](../../../docs/engineering.md)を読み、指摘されたAdvisory／CVE、検査目的、対象Commitを特定する。新規採用、更新、既存運用のどれかを区別する。

実manifest・Lockfile・Workflow・IaC・構築設定から、直接／間接／開発依存、Node、Functions、Actions、Bicep／CLI等の実際の版を確認する。まだmanifestがなければ存在しない依存を検査済みにせず、導入予定の確認として報告する。

## 根拠と判定

- パッケージ配布元・公式Advisory・公式リリース／サポート表を参照し、取得日を記録。Node自身とFunctions側の対応は両方確認する。
- 既知脆弱性は重大度を問わず新規採用・リリース不可。EOLやサポート切れも不可。EOL表がないライブラリは保守・非推奨状況とAdvisoryを確認し、架空の期限を設定しない。
- 全依存を検査する。devDependenciesや実行経路外という理由だけで自動除外しない。検査元停止・未対応・失敗は「不明」であり合格ではない。
- 誤検知・対象版誤りは具体的根拠で説明する。包括的ignore、監査無効化、検査閾値引下げで通さない。
- 未知の脆弱性が存在しないとは保証しない。「検査日時点の既知情報」で評価する。

## 修正

依存経路を確認し、必要十分な更新・除去・代替を選ぶ。Lockfileも更新する。破壊的更新、無関係な大量更新、npm audit fix --forceの無条件実行は避ける。

依存導入時は配布元・名前・install scriptを確認し、不要な秘密やクラウドTokenがない検証環境で扱う。安全性を確認していないコードを高権限で実行しない。

Actionsは正規所有者の完全Commit SHAへ固定し、変更版とその実行ランタイムを確認する。固定するだけで永久に安全とは扱わず更新する。

修正版なしの場合はリリースを止め、除去・代替・機能延期案を提示。稼働中なら悪用可能性・到達性・秘密露出を調べ、停止・遮断・資格情報失効案を示す。実環境変更は既存の承認範囲内のみ。対応期限が未合意なら勝手な「一般標準」を設定せず、人間の判断事項として報告する。

## 検証と出力

更新後は監査再実行、該当単体／契約試験、型・ビルド、影響するUI/APIや配置互換を確認する。監査データ送信先も承認済みRegistryを使用する。実データを第三者の公開検査へ送らない。

対象版、Advisory/EOL出典・確認日、依存経路、修正版、変更、実施試験、未解決、稼働環境への影響、リリース可否を出力する。検査結果に含まれる秘密や環境識別情報は除去する。
